# Ревью PR

Разреши символьную ссылку на этот `SKILL.md`; корень kit (`KIT`) находится на два каталога выше его папки. Текущий каталог — целевой проект (`PROJECT`), возможно с несколькими репозиториями. Прочитай `KIT/AGENTS.md`, применимые инструкции проекта, `KIT/agents/roles/reviewer.md` и `KIT/agents/workflows/review-pr.md`. Правила целевого проекта имеют приоритет; пути kit разрешай относительно `KIT`.

Полный отчёт должен быть в Obsidian, в том числе для самостоятельного ревью без хаба. Установи папку по `KIT/skills/feature-hub/references/artifacts.md`; проектные ссылки/копии оставляй только локально под `.engineering-kit/` после проверки исключения Git. Без доступа к Obsidian отметь сохранение как незавершённое; не требуй регистрации Git-проекта только ради отчёта.

Если ревью относится к задаче хаба, прочитай её задание и актуальные входные/выходные контракты по `KIT/skills/feature-hub/references/artifacts.md`. Сохрани в отчёте ссылку и редакцию задания, ревизии контрактов и влияние замечаний на соседей. Отдельная сессия ревью пишет собственный отчёт под свободным ID, не перезаписывает отчёт реализации и не меняет карту или журнал исполнителя. Передай хабу ссылку для следующего сбора; наличие хаба не является условием обычного ревью.

## Выбор режима

| Запрос | Источник изменений | Рабочая папка |
| --- | --- | --- |
| PR по ссылке или номеру с известным репозиторием | Конкретные target/head PR | По умолчанию detached worktree, в том числе при режиме проекта current |
| Сравнение веток или заданный диапазон | Явные Git-ревизии; для ветки — merge-base..head | В current и при просьбе о локальном сравнении без нового worktree; иначе согласуй изоляцию |
| Текущая работа | Staged, unstaged и новые неигнорируемые файлы относительно HEAD | Исходная копия, без worktree, переключения ветки и переноса правок |

Явный охват пользователя важнее режима по умолчанию. Коммиты ветки не входят в «текущие изменения» автоматически. Для сравнения веток бери base из запроса или согласованной целевой ветки проекта; не угадывай main/master. Без worktree читай файлы нужного коммита через Git, не подменяя их грязной рабочей копией. Автоматических fetch/merge в current нет; актуальность локальных remote-ссылок отметь в отчёте.

## Подготовка источника

1. Сначала установи, что проверяем. Для PR прочитай `KIT/agents/integrations.md`: получи метаданные через доступный MCP, сопоставь локальный репозиторий с target-репозиторием и запиши source/target, их репозитории и SHA. Если данных нет, спроси только недостающее; номер PR не является именем ветки. Jira и внешние MCP необязательны.
2. При повторном запросе найди предыдущий отчёт и состояние задачи по разделу «Повторное ревью» в workflow. Определи, можно ли продолжить прежний снимок или нужна новая подготовка. Не создавай новый worktree только ради продолжения обсуждения.
3. Только если нужен новый worktree, проверь регистрацию (при `kit-git` — через discover) и выбери свободный ID. Одним вопросом согласуй нужные репозитории, source/target, ID и создание worktree, а для нового проекта — также его подключение, если это ещё не согласовано. После согласия подключи новый проект через init по integrations.md. Без `kit-git` — `python3 "KIT/scripts/kit.py" init --project "PROJECT" --repo RELATIVE_PATH`; несколько флагов `--repo` передаются в одном вызове. Не регистрируй все найденные копии автоматически. Повторный init не расширяет регистрацию: если нужного репозитория нет в реестре, согласуй изменение регистрации отдельно. Для локального ревью регистрация не нужна.
4. Подготовь согласованный новый worktree. При `kit-git` вызови `kit_git_prepare` с `mode="review"`, `workspace="worktree"` и параметрами по integrations.md. Без него используй `python3 "KIT/scripts/kit.py" prepare --project "PROJECT" --id ID --repo ALIAS --mode review --base "origin/TARGET" --head "origin/SOURCE" --fetch`. Исходную копию не переключай; зависимости и сервисы не устанавливаются автоматически.
5. После подготовки сверь фактический HEAD worktree с сохранённым head. Для PR дополнительно сравни результат `base` с target SHA, `head` с source SHA и снова получи метаданные PR, если сервис доступен. При изменении любой ревизии останови анализ этого снимка и предложи подготовить актуальный; не подменяй его старой копией. Когда сервис недоступен, явно укажи, какие SHA и сведения об актуальности не удалось проверить.

Fetch помощника работает только через origin. Для fork PR не считай одноимённую ветку origin источником PR: source и target могут принадлежать разным репозиториям. Если точные коммиты уже есть локально, используй их SHA с `fetch=false` (CLI: без `--fetch`). Иначе согласуй способ получения: текущий Git MCP не предоставляет произвольный fetch другого remote. Remote, права и способ авторизации автоматически не меняй. Ошибка получения коммитов останавливает подготовку; ограниченное ревью по доступному API-diff возможно только как явно оговорённый охват.

Для связанного репозитория подготавливай отдельный worktree под тем же ID только при необходимости и после согласования. Выбранную ревизию запиши; неизвестная совместимая версия потребителя — ограничение проверки. Не создавай рабочие копии всех репозиториев автоматически.

## Ревью и завершение

Передай в `KIT/agents/workflows/review-pr.md` выбранный режим, источник, ревизии и пути. Там определены получение контекста, анализ, отчёт и повторная проверка; роль reviewer задаёт качество замечаний и порядок их согласования. Работай последовательно, без обязательных дополнительных агентов.

После завершения обсуждения предложи предпросмотр очистки только существующих worktree этого review ID по `KIT/skills/workspace-cleanup/SKILL.md`. Сначала сохрани отчёт вне worktree; удаление требует отдельного согласия. В режиме без worktree не вызывай cleanup и не удаляй исходную папку или каталог отчёта. Создание PR и исправление кода не входят в ревью.
