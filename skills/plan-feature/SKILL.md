# Фича от плана до проверки

Разреши символьную ссылку на этот файл; корень kit (`KIT`) находится на два каталога выше его папки. Прочитай `KIT/AGENTS.md`, роль tech-lead и `KIT/agents/workflows/plan-feature.md`. Пути kit разрешай от `KIT`; применимые правила целевого проекта — от проекта. Читай роли по мере использования, работай последовательно.

До сохранения плана установи папку задачи в Obsidian по `KIT/skills/feature-hub/references/artifacts.md`, в том числе без хаба. Там должны быть полные план и отчёт; проектные ссылки/копии допустимы только локально под `.engineering-kit/` после проверки исключения Git. Папка хаба, если она уже определена, задаёт путь для этой задачи.

## Если задача передана хабом

До подготовки Git прочитай указанную редакцию задания, навигацию хаба и `KIT/skills/feature-hub/references/artifacts.md`. Установи TASK_ID, общую папку, владельца журнала и разрешённую стадию. Открытие задания само по себе не разрешает реализацию. Если пользователь просит только принять задачу/прочитать вводные, запиши принятие и понимание задачи, затем остановись перед планированием или кодом согласно запросу.

Прочитай только названные разделы PRD/Jira, актуальные формы входных контрактов, связанные решения и ограничения данных. Сохрани ID критериев, версии и приоритет источников. Сверь вводные с фактической версией кода: запись хаба не подтверждает, что нужная зависимость уже есть в рабочей копии. Отсутствующий контракт или конфликт подними пользователю и в журнале; останови только зависимую стадию, продолжая разрешённую работу без этого решения. Не угадывай интерфейс и не меняй требования молча.

Если у задачи уже есть сессия-владелец, перед записью нужна передача по формату артефактов. Иначе начни свой журнал при принятии задачи, затем пополняй при решениях, изменениях контрактов и перед паузой. Хаб, карту, задания и чужие журналы/контракты не редактируй. После подготовки свяжи TASK_ID с уникальным RUN_ID и фактическими путями; не используй ID хаба как общий Git ID всех задач.

Согласованный план из прежней сессии используй после сверки его входов и актуальности. Если решение не меняется и реализация уже поручена, повторное согласование не требуется. При новой редакции задания/контракта проверь влияние до продолжения зависимой работы; при изменении согласованного решения верни вопрос пользователю.

## План и реализация

1. Установи каталог проекта, прочитай `KIT/agents/integrations.md` и применимые инструкции репозиториев. При доступном `kit-git` выполни discover, а для нового проекта согласуй состав и вызови init по этому документу. Для Jira/Confluence используй MCP, project keys задавай отдельно от секретов. Без Git MCP прежний `python3 KIT/scripts/kit.py init --project PROJECT` остаётся вариантом при наличии прав. Не выводи конфигурацию целиком.
2. Прочитай режим из discover. В current начинай задачу в исходной папке на сохранённой ветке разработки: `kit_git_prepare(id, repo, confirm=true)` без base/head/fetch. Не спрашивай о создании worktree для каждой задачи; переключение ветки и включение уже существующих правок согласуются отдельно по integrations.md. В worktree после чтения постановки предложи репозитории, ID и базовые ветки одним вопросом; после согласия подготовь копии. Для разовой изолированной задачи в current можно явно выбрать `workspace="worktree"` с новым ID. Это не разрешение менять код до утверждения плана. Подготовка обязательна до анализа кода, в том числе при запросе только плана. В worktree используй `kit_git_prepare(id, repo, mode="feature", base="origin/BASE", fetch=true, confirm=true)` от согласованной базы (обычно main); после уже данного согласия приступай без повторного вопроса. Анализируй файлы подготовленной копии и зафиксируй её путь, ветку и base/head SHA. Чтение `origin/main` через `git show` не заменяет worktree. Если запрос ограничен чтением требований без анализа кода, подготовка не нужна.
3. Выполни plan-feature: критерии с ID, что входит и что отложено, варианты и trade-offs, последовательные шаги и проверки. Сохрани согласуемый план в выбранной папке Obsidian с уникальным ID задачи и источниками требований. В `PROJECT/.engineering-kit/runs/ID/plan.md` при необходимости оставь локальную ссылку по правилам хранения. До согласования кода не меняй.
4. После утверждения плана продолжи реализацию, если она уже поручена. Используй подготовленные пути задачи; не создавай дубликаты. В current это исходная копия, в worktree — отдельные копии. Если подготовки ещё нет, выполни предыдущий шаг. В обычном режиме без Git MCP прежний CLI prepare создаёт worktree в пределах прав. Не переноси незакоммиченные изменения между копиями.
5. В роли developer меняй только согласованные пути задачи. Передай qa и reviewer исходные критерии, изменённые участки и результаты команд, прочитав их инструкции. Для QA используй `KIT/agents/workflows/verify-feature.md`; в этой же сессии включи результаты в основной отчёт, отдельная сессия `$verify-feature` создаёт собственный отчёт. Это последовательные роли, а не независимая экспертиза. Для добавления репозитория повтори prepare с тем же ID в том же режиме. Изменение согласованной архитектуры или новые зависимости требуют согласования.
6. Сохрани полный результат в выбранной папке Obsidian: по критериям — статусы с доказательствами, команды, замечания и риски; укажи пути, ветки, SHA и охват незакоммиченных изменений. Для задачи хаба добавь редакцию задания и контрактов, ссылки на QA/review и воспроизводимое состояние кода по формату артефактов. В `PROJECT/.engineering-kit/runs/ID/report.md` при необходимости оставь локальную ссылку. Отчёт и план остаются за пределами удаляемых worktree.
7. После запроса на коммит покажи предпросмотр состава и текста через `kit_git_commit_preview`, согласуй его и используй `kit_git_commit` по integrations.md. Если пользователь явно выбрал общую политику `local_commit=auto`, локальный коммит файлов порученной задачи выполняется после проверок и preview без нового вопроса; ограничения и исключения — в integrations.md. Push — только по отдельному поручению через preview/push. Создание PR запрещено. Если изменения не сохранены, worktree остаётся нужен. Очистка после согласования точных путей — по `KIT/skills/workspace-cleanup/SKILL.md`; ветки не удаляются.
   Для current исходная папка остаётся после завершения задачи; cleanup ей не нужен и не может её удалить. Merge в целевую ветку не является частью commit/push и не выполняется автоматически.

Для задачи хаба перед завершением или паузой обнови актуальный итог журнала: сделанное, фактические QA/review, состояние кода, хвосты и что должны знать соседи. В своих контрактах поддерживай актуальную форму, ревизию и историю, разделяя согласование, реализацию и интеграцию. Верни ссылку на журнал и основной отчёт для следующего сбора хаба. Если отчёт/журнал недоступен для записи, явно укажи, что передача не завершена, и дай результат в диалоге; не объявляй фичу принятой. После новых правок или commit/push обнови сведения о состоянии и ссылках, не перенося старые проверки на изменённый код автоматически.

Планирование само по себе не разрешает реализацию. Смена рабочей папки для shell-команд не переносит сессию и не расширяет её sandbox: при необходимости запроси штатный доступ к каталогам, не обходи ограничения.
