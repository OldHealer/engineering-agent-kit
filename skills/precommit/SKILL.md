# Проверка перед коммитом

Разреши символьную ссылку на этот файл; корень kit (`KIT`) находится на два каталога выше его папки. Прочитай `KIT/AGENTS.md`, применимые инструкции целевого проекта и правила Git из `KIT/agents/integrations.md`. Работай в существующей копии, без создания worktree, fetch и переключения веток ради проверки. Сохраняй выбранный режим current/worktree. Проверки выполняй последовательно; отдельные агенты не требуются.

## Состав и состояние

1. Установи выбранные репозитории и состав задачи из запроса, плана и уже согласованного списка файлов. При доступном Git MCP используй discover/status, не регистрируй проект только ради проверки. Без MCP допустимо Git-чтение в cwd каждого репозитория. Не включай соседние репозитории автоматически.
2. Сначала получи **имена и статусы**, без содержимого: `git status --porcelain=v1 -z --untracked-files=all`, `git diff --name-status -z`, `git diff --cached --name-status -z`, `git ls-files --others --exclude-standard -z`. Обрабатывай NUL-разделители; учитывай оба пути переименования. Установи HEAD, ветку, staged/unstaged и незавершённые операции. Для пустого репозитория не предполагай наличие HEAD. Для явно выбранного диапазона сначала получи список имён именно из него; локальный status не перечисляет файлы уже созданных коммитов.
3. Проверь имена до чтения файлов/diff: `.env*`, ключи, пути с credentials/secret, личные `.engineering-kit` и другие запрещённые активной политикой пути. Не открывай их даже для поиска секрета. Переименование из запрещённого пути также исключает чтение diff и нового содержимого до отдельного решения по доступу. Попадание такого пути в staged или предлагаемый commit — блокировка; оставленные вне commit локальные файлы отметь как исключённые. Не выводи найденные секреты или полные конфиги. Проверка имён не гарантирует отсутствие секретов в разрешённых файлах; используй существующий безопасный scanner проекта, если он есть, без раскрытия значений.
4. По умолчанию охват — выбранные staged + unstaged + новые неигнорируемые файлы задачи. После фильтрации читай diff с **явными разрешёнными путями после `--`** и содержимое выбранных новых файлов; общий `git diff` до фильтрации не используй. Удалённый файл проверяй по diff, не пытайся его открыть. Проверку ветки/диапазона выполняй только по явному запросу с точными ревизиями; `origin/main...HEAD` не заменяет локальные изменения. Если нужного коммита нет, сообщи ограничение, не подменяй базу. Запуск тестов в грязной копии не подтверждает отдельно выбранную ревизию.
5. Разбери untracked: целевые новые модули, тесты, миграции и данные должны попасть в предлагаемый состав, если на них зависит реализация. Известную чужую работу/scratch оставь вне состава. Не спрашивай повторно о уже согласованных файлах; задай один вопрос только о неясных файлах, влияющих на комплектность. Не делай add/reset/удаление/правку ignore. Для частично staged файла явно различай содержимое индекса и рабочей копии: commit Kit выбирает целые файлы, а не hunks.

Чистая копия без кандидата — «нет изменений для нового commit», а не успешная проверка неизвестных коммитов. Если выбранный состав пуст, не запускай несвязанные проверки.

## Проверки проекта

- Найди команды в инструкциях, manifest/scripts, конфигурациях lint/types/tests и CI целевого репозитория. Прочитай фактические scripts до запуска; имя lint/test не доказывает отсутствие побочных действий. Выполни обязательные проектные проверки и релевантные тесты в изученном изолированном окружении. Не запускай hooks вслепую: они могут форматировать файлы, обращаться к рабочим сервисам или публиковать данные.
- Не выполняй автофикс/форматирование и не меняй исходники в рамках проверки. Не запускай миграции БД, сервисы, установку пакетов или контейнерные команды по примеру чужого проекта. Если выполнение требует отдельного действия, учитывай существующее поручение и политику автономии; сам вызов precommit не расширяет разрешения. Невозможность запуска проверки отделяй от дефекта кода.
- Для нетривиальных изменений поведения, исправлений и интеграций сопоставь сценарии с содержательными тестами или иными воспроизводимыми проверками. Изменение одних моков и `mock.called` не доказывает поведение. Наличие нового публичного def/if само по себе не требует отдельного теста; для косметики и обратимых правок без поведения не добавляй тест ради строки покрытия. Пробелы в обязательном покрытии отмечай как блокировку; отсутствие доступной среды — как «не проверено».
- Применяй стековые требования **из целевого проекта**: например, Python lint/pytest, frontend lint/types/tests, статическую проверку графа миграций. Формат логирования, язык комментариев, docstrings/type hints, CHANGELOG, TODO/FIXME со ссылкой, допустимые migration heads и ограничения данных проверяй по действующим правилам, не навязывай conventions Gradient другим проектам. Для docs-only запускай только применимые проверки документов/ссылок и обязательные команды проекта.
- Повторно используй результаты текущей задачи, если известны точная команда, окружение, результат и проверенные входы, которые не менялись. Одинакового HEAD недостаточно при незакоммиченных правках. После изменения кода/конфигурации/состава повтори затронутые проверки; не повторяй весь suite без причины. Если после тестов изменились исходники или индекс, обнови проверяемый снимок и готовность.

## Обычный commit и merge

Precommit сам не меняет индекс, не делает commit/push/PR и не исправляет конфликты. Если его вызвали внутри уже разрешённого commit-сценария, после проверки верни управление вызывающему сценарию без повторного согласования уже разрешённых действий. Не вызывай precommit рекурсивно из него самого или из прочитанного общего правила «запустить precommit».

- **Обычный commit:** передай явный список проверенных целых файлов. Git MCP требует отсутствия заранее staged изменений; если индекс уже заполнен, сообщи отдельную блокировку выполнения commit, даже когда проверки кода прошли. Не очищай и не переноси индекс автоматически. Последующие commit_preview/commit сохраняют существующую политику согласования состава и текста.
- **Управляемый merge:** через status проверь исходный HEAD, MERGE_HEAD/обоих родителей, конфликты и blockers. После обычного редактирования разрешённых файлов проверь весь итоговый кандидат, включая автоматически объединённые и staged изменения, а не только ручное разрешение. Если аргументы уже определены, используй read-only `kit_git_commit_preview(mode="merge", resolved_files=[...], message, author?)` для точного состава; текст/identity не выдумывай ради preview. При отсутствии preview полноту кандидата отметь как предварительную, окончательный состав сверяется вызывающим commit-сценарием. Нельзя применять обычное требование пустого индекса к merge, передавать частичный files или делать shell git add. Unmerged индекс после исправления файла допустим для preview только с явным resolved_files; наличие маркеров/неисправленного конфликта блокирует завершение.
- **Rebase/cherry-pick, чужой merge или изменившиеся родители:** сообщи блокировку, не пытайся закончить операцию. Конфликт в запрещённом файле не читай. Отмену merge и потерю правок не предлагай как автоматическое средство пройти precommit.

## Результат

По каждому репозиторию покажи путь/ветку/HEAD и охват, точный предлагаемый состав, исключённые/неясные файлы, команды и результаты, отдельно блокировки, предупреждения и непроверенное. Для merge укажи обоих родителей и источник полного состава. Различай «готовность проверенного состава подтверждена», «есть блокировки», «готовность не подтверждена» и «нет изменений». Ошибка обязательной команды или неразобранный целевой файл не дают готовности; незапущенная проверка не считается пройденной. Предупреждение само по себе не требует нового разрешения, если оно не меняет согласованные критерии/последствия.

Сохрани полный результат в существующем отчёте своей задачи в Obsidian; без такого отчёта выбери папку и свободный ID по `KIT/skills/feature-hub/references/artifacts.md`. Соблюдай владение отчётом и блок сведений о сессии. Проектные ссылки/копии — только локально в игнорируемой `.engineering-kit`, без commit/push. При невозможности сохранения сообщи, что не передано, и верни доступный результат в диалоге.

Закончи конкретным следующим шагом: исправление найденного, недостающая проверка, решение по составу или передача проверенного списка в commit_preview. Пройденный precommit не означает разрешённый commit или приёмку фичи. Для полного ревью PR и проверки критериев фичи доступны отдельные review-pr/verify-feature.

Пример: `$precommit Проверь текущие изменения задачи перед коммитом. Код и индекс не меняй.`
