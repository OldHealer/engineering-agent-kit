# Артефакты хаба и сессий задач

Пользователь хранит рабочие артефакты лично: полные документы должны быть в Obsidian, проектные копии не коммитятся и не отправляются. Основная общая папка `FEATURE` по умолчанию — каталог фичи в Obsidian. Путь к vault и папке задачи бери из запроса, личной политики artifact-root или существующего хаба; если его нельзя установить однозначно, согласуй один раз, а затем передавай через задания и ссылки. Не считай пути-заглушки из примеров настроенной папкой. Не создавай документы в корне vault без выбора папки проекта/задачи.

Ниже имена по умолчанию; у существующей фичи сохрани её имена и запиши соответствие в хабе. Форматы — Markdown, без нового реестра Git и обязательных зависимостей. Для самостоятельного ревью, исследования или QA без хаба выбери папку задачи в Obsidian по тем же правилам; наличие хаба и регистрация проекта для этого не обязательны.

## Размещение и владение

| Артефакт | По умолчанию | Единственный писатель |
| --- | --- | --- |
| Навигация, источники, решения и последний сбор | `FEATURE/hub.md` | хаб |
| Карта задач и зависимостей | `FEATURE/tasks.md` | хаб |
| Неизменяемая редакция задания | `FEATURE/tasks/TASK_ID/brief-vN.md` | хаб |
| Текущее состояние задачи и лента событий | `FEATURE/tasks/TASK_ID/journal.md` | сессия задачи |
| Актуальный контракт с историей | `FEATURE/contracts/NAME.md` | назначенная задача-владелец |
| План и итог реализации | `FEATURE/tasks/TASK_ID/plan.md`, `report.md` | сессия задачи |
| QA-отчёт | `FEATURE/checks/CHECK_ID.md` | сессия проверки |
| Review-отчёт | `FEATURE/reviews/REVIEW_ID.md` | сессия ревью |

`TASK_ID` — устойчивый ID задачи в фиче; `RUN_ID` — отдельный уникальный ID подготовки Git/результатов, `CHECK_ID` — уникальный ID проверки. Связь запиши в журнале и карте. Не переиспользуй чужой RUN_ID и не создавай фиктивный `state.json`: это файл Git backend. Задание может ещё не иметь RUN_ID, пока задача не подготовлена.

Хаб сохраняет ссылки на отчёты, а не их редактируемые копии. Журнал хранит краткий результат и влияние на соседей; подробные проверки находятся в основном отчёте. Отчёты и общая папка должны находиться вне удаляемых worktree. В `PROJECT/.engineering-kit/runs/RUN_ID/plan.md` и `report.md` при необходимости оставь ссылки на полные документы Obsidian. Одна ссылка в Obsidian на документ, который существует только в проекте, не выполняет требование пользователя.

## Локальные копии и полнота передачи

Если пользователь явно выбирает проектную папку основной, согласуй путь её полной копии в Obsidian. Сохрани в хабе соответствие путей и какой экземпляр основной. Копию обновляет тот же владелец при сохранении значимого решения, перед паузой и передачей результата; отметь источник и редакцию копии, не редактируй её как отдельный оригинал. Фоновой синхронизации нет. Для Obsidian соблюдай блок сессии ниже. Исходные PRD копировать не обязательно: требования можно связывать ссылками, но созданные планы, задания, журналы, контракты и отчёты должны быть доступны в Obsidian полностью.

Все проектные документы этого процесса размещай только под `PROJECT/.engineering-kit/`, вне worktree. До их создания проверь, что Git их игнорирует и уже не отслеживает (`git check-ignore`, `git ls-files` по конкретным путям). При регистрации проекта Git MCP добавляет локальный `/.engineering-kit/` в `.git/info/exclude`, когда исходный репозиторий совпадает с PROJECT; в проекте с несколькими репозиториями служебная папка лежит над ними. Не меняй общий `.gitignore` приложения ради личных артефактов. Если исключение не настроено, сохраняй полный документ в Obsidian без проектной копии; не регистрируй проект только ради отчёта и не обходи защиту Git-метаданных через shell.

Kit Git MCP блокирует `.engineering-kit` в выбранных файлах коммита, в отслеживаемых файлах и в новых коммитах перед push. Это защита операций kit, не запрет ручных Git-команд вне kit. Если артефакт уже отслеживался или попал в историю, сообщи об этом; удаление из индекса или переписывание истории автоматически не выполняй. Служебные `state.json`, `project.json`, блокировки и временные файлы остаются локально, в Obsidian их зеркалировать не требуется. Секретные файлы не копируются.

Запись в Obsidian не расширяет sandbox. При отказе используй штатный запрос доступа к выбранной папке; не меняй профиль и не считай проектную копию заменой сохранению в Obsidian. Если сохранение там не выполнено, явно отметь незавершённую передачу и верни доступный результат в диалоге, не объявляя артефакты сохранёнными.

Перед записью установи владельца. Возобновлённая/новая сессия может продолжить задачу после явной передачи и подтверждения, что прежняя сессия больше не пишет. Хаб записывает передачу в карту; новый владелец — в свой журнал/контракт. QA и reviewer создают собственные отчёты, не изменяют журнал исполнителя или карту. Запрос на правку чужого файла передавай через свой артефакт.

## Сведения о сессии в Obsidian

Во всякой создаваемой или дополняемой заметке Obsidian сразу после заголовка обнови/добавь `> [!info] Сессия Codex`: достоверные директория запуска и ID, команды `cd DIRECTORY` + `codex resume SESSION_ID`, а также `cd DIRECTORY` + `codex "ТЕМА"` для новой сессии. Пути с пробелами заключай в кавычки. Блок этой сессии не дублируй, сведения Claude Code сохраняй.

Если ID неизвестен, прямо укажи это и дай `codex resume` для выбора сессии. Для чата только в десктопном приложении укажи, как найти его там; продолжение через CLI обещай лишь при подтверждённой доступности. Директорию запуска не подменяй текущим worktree. Этот блок добавляется ко всем шаблонам ниже при работе в Obsidian; в обычном проектном каталоге достаточно известных сведений в хабе/журнале.

## Хаб и карта

Минимальное содержание хаба:

```markdown
# FEATURE_ID — название

- Проект и общая папка: пути
- Карта задач: ссылка
- Источники: документ, версия/дата/отпечаток, ссылка, согласованный приоритет
- Сквозные критерии: ID, формулировка, источник, способ приёмки
- Решения и вопросы: дата, решение/вопрос, источник, затронутые задачи
- Последний сбор: дата, прочитанные артефакты, последние записи/ревизии
- Следующий шаг: задача, доступная стадия, основания и блокеры
```

В карте для каждой задачи нужны ID/Jira, требования и критерии с ID, репозитории, ссылки на задание/журнал/план/отчёты, владелец, потребляемые и выставляемые контракты с ревизиями. Зависимость записывай как `от кого/чего → требуемое условие → какую стадию держит → доказательство/неизвестно`.

Готовность показывай отдельными полями: реализация; QA; review; интеграция; развёртывание; приёмка. Для каждого факта — источник, дата и версия кода/стенда, когда применимо. Общая стадия вроде «в работе» удобна для навигации, но не заменяет эти поля. У внешней задачи дополнительно укажи, кем сообщено и что удалось проверить.

## Задание сессии

```markdown
# TASK_ID — задание, редакция N

- Фича, проект, карта и журнал: ссылки/пути
- Разрешённая стадия: чтение и планирование / реализация после согласованного плана
- Цель и границы: что входит; что явно вне задачи
- Источники: конкретные разделы PRD/Jira, версии и приоритет
- Критерии: ID → точная формулировка → источник → способ проверки
- Репозитории и исходное состояние: известные ветки/SHA, режим проекта либо «уточнить»
- Зависимости: условие, стадия, подтверждение или блокер
- Входные контракты: ссылки, ревизии и нужные гарантии
- Выходные контракты: что задача обязана определить и кто потребляет
- Ожидаемый результат: код, проверки, основной отчёт и влияние на соседей
- Известные ограничения: данные, доступы, стенд и открытые решения
```

Задание ссылается на первоисточники; не копируй весь PRD. В нём не должно быть поручений публиковать комментарии или менять Git, которых пользователь не давал. При разночтении источников не выдумывай приоритет. Согласованный план, перенесённый из другой сессии, можно использовать после сверки входных версий; не требуй повторного согласования без изменения решения.

## Журнал и результат

```markdown
# TASK_ID — журнал

- Задание: ссылка и редакция
- Владелец/сессия: известные сведения
- RUN_ID, рабочие пути, ветки: известное либо «не подготовлено»
- Стадия и блокеры: текущее состояние
- План и основной отчёт: ссылки
- Актуальный итог: результат, состояние кода, влияние на соседей, хвосты

## Лента

### Дата — событие
Прочитанные источники/решение/проверка/изменение контракта, доказательство, кого касается.
```

Начинай журнал при принятии задачи, пополняй при значимых решениях и перед паузой. Лента дописывается, шапка и актуальный итог обновляются. События не удаляй. На завершении укажи сделанное по критериям, результаты QA/review, состояние кода и незакоммиченные изменения, ревизии контрактов, влияние на соседей и нерешённое. Реализация с незакоммиченным кодом может быть готова к проверке; это не означает интеграцию или приёмку.

Для воспроизводимости отчёта укажи по каждому репозиторию путь, ветку, base/head SHA и охват staged/unstaged/новых файлов. При грязной копии нужен отпечаток проверяемого состояния (diff, индекс и новые файлы) либо сохранённый снимок разрешённых файлов вне worktree, без секретов; если его нет, явно отметь невозможность подтвердить прежнее состояние. Для проверки на стенде нужны версия сборки, данные и окружение. При изменении относящихся к проверке входов её результат требует повторной сверки.

## Контракт

```markdown
# Контракт: NAME

- Владелец: TASK_ID; потребители: ID задач
- Ревизия: N; состояние: черновик / согласован / реализован
- Подтверждение реализации: репозиторий, путь, SHA или состояние рабочей копии

## Актуальная форма
Имена, сигнатуры, схема, инварианты и пример. Это действующая версия целиком.

## Основания
Требования и согласованные решения.

## История
Дата — ревизия — изменение — затронутые потребители — требуемая повторная сверка.
```

Согласованный контракт может ещё не быть реализован или влит: эти факты фиксируй раздельно. При изменении обнови актуальную форму, увеличь ревизию и допиши историю со ссылкой из журнала. Не заставляй потребителя восстанавливать текущую сигнатуру по всей ленте. Готовность потребителей к новой ревизии отмечает хаб по их результатам, не владелец контракта за них.
