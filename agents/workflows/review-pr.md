# Workflow: review-pr

## Назначение

Провести самостоятельное ревью текущих изменений, ветки или PR без запуска полного процесса разработки.

## Источник и контекст

Прочитай `agents/roles/reviewer.md` и применимые инструкции целевого проекта и вложенных каталогов. Режим и подготовка окружения описаны в `skills/review-pr/SKILL.md`; без изоляции не требуй регистрации проекта или создания worktree.

Установи цель изменения по запросу пользователя, описанию PR и доступной связанной постановке. Прочитай относящиеся к задаче обсуждения; при наличии ссылки и MCP можно получить Jira/Confluence по `agents/integrations.md`. Не требуй этих сервисов, task key или вложений для каждого ревью. Если важного требования не хватает, задай конкретный вопрос; техническую часть можно проверить с явно указанным ограничением.

Сохрани заданные пользователем критерии и их ID; при отсутствии ID используй `AC-1`, `AC-2`, … для установленных требований. Не придумывай требования из реализации. Кратко объяви репозитории, источник, ожидаемое поведение и границы проверки. Если доступны комментарии PR, учти уже обсуждённые проблемы до составления списка замечаний.

## Порядок ревью

1. **Зафиксируй проверяемое состояние.** Для PR нужны target/head SHA и merge-base, для ветки — выбранные base/head и merge-base, для явного диапазона — его границы, для текущей работы — HEAD и состав staged/unstaged/новых файлов. Если первого коммита нет, отметь отсутствие HEAD и проверь индекс/новые файлы по роли reviewer. При worktree используй сохранённые ревизии из prepare. Не смешивай режимы и не подменяй недоступный diff пустым результатом. Для текущей работы проверь перед завершением, что проверенный набор и содержимое файлов не изменились; иначе обнови анализ.
2. **Определи изменения безопасно.** Сначала получи имена и статусы файлов, затем diff разрешённых путей и их контекст. При переименовании учитывай оба пути; секретные файлы и ключи не читай и не сохраняй в diff/отчёт. Для PR и ветки diff идёт от merge-base до зафиксированного head, а содержимое файлов читается из той же ревизии. Усечённый API-patch и неполный список файлов не подтверждают полный охват: используй локальный Git либо отметь непроверенную часть. Пропуски перечисли явно. При пустом наборе изменений сообщи об этом и сохрани результат без обхода всего проекта.
3. **Выполни релевантные проверки инструментами** по `AGENTS.md`. Изучи вызываемые scripts, выбери существующие команды без автоисправлений и согласуй необходимые зависимости отдельно. Зафиксируй рабочую папку и проверяемую версию. Если в режиме без worktree рабочая копия отличается от выбранного коммита, её тесты не подтверждают этот коммит: пропусти их с причиной или согласуй изоляцию. Отделяй найденные ошибки от невозможности запуска. Ошибки в неизменённых файлах не скрывай, но без сравнения с базой не объявляй их вызванными PR. Повторяющиеся диагностики одной причины можно сгруппировать, сохранив затронутые пути.
4. **Проверь смысл и последствия изменений** по разделу «Качество ревью» в роли reviewer. Свяжи установленное требование с реализацией и доказательством: кодом, существующим тестом или результатом запуска. Затем проверь зависимых потребителей, включая другой репозиторий без своего PR, если изменился внешний контракт. Указывай ревизии связанных репозиториев; не считай случайную локальную ветку совместимой. Когда контракт не меняется, отдельный обход всех репозиториев не нужен.
5. **Перепроверь кандидатов.** Попытайся опровергнуть каждый вывод по коду и тестам. Объедини одну причину в одно замечание с нужными ссылками, не дублируй результат инструмента отдельной находкой. В замечания включай подтверждённое; недостаток данных остаётся вопросом или ограничением. Число проходов и согласившихся ролей не заменяет доказательства. Пустой список замечаний допустим.
6. **Сохрани результат до начала обсуждения**, затем примени процедуру «Серьёзность и разбор замечаний» из роли reviewer. После каждого ответа обновляй решение в отчёте. Для публикации используй `agents/integrations.md`; локальный запуск и отсутствие принятых замечаний не требуют публикации. После завершения действуй по разделу завершения в skill, если он использовался.

## Отчёт

При запуске через skill выбери свободный ID, если его не выдала подготовка, и сохрани полный отчёт в выбранной папке Obsidian по `skills/feature-hub/references/artifacts.md`. Для задачи хаба это `FEATURE/reviews/ID.md`; в `PROJECT/.engineering-kit/runs/ID/report.md` при необходимости оставь локальную ссылку после проверки исключения Git. Для локального ревью создаётся только отчёт: не создавай фиктивный state.json и не регистрируй исходную папку как worktree. При прямом вызове workflow достаточно отчёта в диалоге, если файл не запрошен; при сохранении файла правило Obsidian действует. Недоступность записи обозначь явно, не расширяя права автоматически.

В отчёте нужны:

- источник и цель, PR/репозитории, режим, проверенные ревизии и связь с предыдущим отчётом;
- охват и исключения, критерии с результатом `пройден`/`не пройден`/`не проверен` и доказательством, отдельно анализ кода и фактический запуск;
- команды: папка, ревизия, lint/types/tests, результат или причина пропуска;
- замечания с постоянными ID и полями из роли reviewer, вопросы, ограничения и вердикт;
- отдельно история решений пользователя и результаты публикации.

Полнота проверки и принятие риска — разные вещи: ответ «отклонено» не превращает доказанную проблему в отсутствие дефекта. Если замечаний нет, перечисли проверенные области и ограничения, без обещания отсутствия всех ошибок.

## Повторное ревью

Найди предыдущий отчёт по ссылке PR, репозиторию и известному ID; состояние ранее подготовленного worktree проверь через status. Для локального отчёта без worktree status не требуется. Если есть несколько подходящих запусков, уточни только выбор. Если прошлые замечания недоступны, сообщи это и проведи новое ревью без обещания проверить старый список.

- **Продолжение обсуждения того же состояния:** сохрани ID замечаний и решения. Ранее подготовленный worktree можно использовать только если он существует, его HEAD и проверяемые файлы соответствуют сохранённой ревизии, а target/head PR не изменились. Не запускай prepare повторно для занятого ID. Если пользователь просит новое ревью, а не продолжение разбора, повтори необходимый анализ и проверки.
- **Новые ревизии:** подготовь новый снимок под новым ID по skill; старый отчёт и worktree не перезаписывай и не обновляй через pull/reset. Сравни снимки, проверь исправления и новое влияние в полном актуальном охвате PR. Для локальной незакоммиченной работы тоже нужен новый проход: одинаковый HEAD не означает одинаковые изменения.
- Для каждого прежнего ID укажи `исправлено`, `остаётся` или `не проверено`, с доказательством. Для той же проблемы сохраняй ID, новые нумеруй после наибольшего прежнего номера. Вопросы и допущения не переименовывай в исправленные дефекты. Историю решений сохрани со старой ревизией; на новом снимке не переноси автоматически принятие и разрешение на публикацию. Нужен разбор актуальных замечаний по роли reviewer. Уже опубликованный комментарий не создавай повторно без проверки дублей.
