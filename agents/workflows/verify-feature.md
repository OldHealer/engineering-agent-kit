# Workflow: verify-feature

## Подготовка

1. Установи задачу/фичу, источники и согласованные критерии с ID. Для фичи возьми сквозные критерии PRD и хаба, для задачи — её задание и план. Противоречия покажи, не выбирая удобную версию. При отсутствии критериев предложи их пользователю; анализ доступного кода возможен, вывод о приёмке — после согласования.
2. Зафиксируй для каждого репозитория фактические путь, ветку, base/head SHA и наличие staged/unstaged/новых файлов; для стенда — версию сборки и известные данные. Не подменяй нужный коммит текущим checkout. Подтверждение dirty-состояния описано в `KIT/skills/feature-hub/references/artifacts.md`; без него явно ограничь воспроизводимость. Если версии компонентов неизвестны или недоступны, отметь, какие критерии это не даёт проверить.
3. Изучи отчёт исполнителя и прошлые QA/review-результаты. Используй их как свидетельства с указанным источником, не объявляй своим запуском. Результат другой версии не переноси автоматически. Найди реальные потребители изменённых контрактов, в том числе в репозиториях без правок; не требуй проверки всех репозиториев без связи с критериями.
4. Составь связь `критерий → сценарий → уровень проверки → данные/окружение → ожидаемое наблюдение`. Учитывай границы, ошибки и регрессии затронутого поведения. Неполные данные или доступы могут мешать только части критериев. Синтетический набор подходит для проверки формулы, но не доказывает полноту загрузки на настоящем стенде.

## Выполнение

Команды бери из правил и scripts целевого проекта. Перед запуском прочитай их фактическое действие; покажи команду и рабочий каталог. Не запускай автоисправление, установку зависимостей, watch, деплой, пересчёт рабочей БД или внешнюю запись по одному поручению «проверь». Для тестов, создающих данные, установи, что используется выделенное тестовое окружение; если это неизвестно, запроси недостающее условие и продолжай безопасные проверки.

Выполни доступные проверки. По каждому критерию сохрани один из результатов:

- `пройден` — нужное поведение проверено запуском с ожидаемым результатом либо это статический критерий с доказательством по файлам;
- `не пройден` — есть наблюдаемое расхождение с согласованным ожиданием;
- `не проверен` — выполнение или доказательство недоступно; чтение кода вместо требуемого запуска, неизвестная версия стенда, отсутствующие данные.

Lint, types и tests показывай отдельно: `пройдено`, `найдены ошибки`, `не удалось запустить`, `пропущено`, с существенной диагностикой. Не своди ненулевой exit code к дефекту продукта. Укажи, проверено ли происхождение ошибки сравнением с исходной версией; иначе оно неизвестно.

Не исправляй реализацию в ходе QA. Для дефекта дай ID, критерий, шаги, ожидаемое/фактическое поведение и доказательство. Согласованный возврат на исправление выполняется сессией задачи; новое состояние требует новой проверки. Автоматического бесконечного цикла исправлений нет.

## Завершение

Перед сохранением сверь, что код/сборка и релевантные входы не изменились во время проверки. При изменении отметь затронутые результаты как требующие повторной проверки; прежний успех не подтверждает новую версию.

Сохрани QA-результаты по шаблону skill: результаты всех критериев, версии, команды, дефекты, непроверенные области и рекомендация. В составе plan-feature в той же сессии это раздел основного отчёта реализации; отдельная сессия verify-feature создаёт собственный QA-отчёт. Для Obsidian добавь сведения о сессии по формату артефактов. Передай хабу ссылку и влияние на готовность, не меняя карту самостоятельно.

Для сквозной приёмки проверь совместимость фактически собранных компонентов и сценарии PRD. Зелёные unit-тесты отдельных задач не закрывают сквозной критерий. Если все критерии пройдены, рекомендуй приёмку; при дефектах — доработку; при оставшихся непроверенных критериях — перечисли недостающие проверки. Решение пользователя принять риск сохрани отдельно, оно не меняет результат проверки.
