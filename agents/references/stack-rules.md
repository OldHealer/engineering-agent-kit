# Правила реализации по затронутому стеку

Применяй только релевантные разделы после чтения правил и кода проекта. Это отобранные ограничения из language/library skills `gradient-ai-box`, без привязки к его CLI. Они не требуют менять стиль, архитектуру или зависимости существующего проекта.

## Python и асинхронный код

- Проверяй изменяемые аргументы по умолчанию и владение передаваемыми коллекциями: состояние одного вызова не должно неожиданно переходить в следующий.
- В async-пути найди блокирующие операции и существующий в проекте способ их выполнения. Проверь время жизни сессий/клиентов, обработку отмены и освобождение ресурсов при ошибке. Не переноси ORM-сессию в другой поток без поддержки её API.
- Перехватывай исключение там, где есть определённое восстановление или преобразование ошибки. Не скрывай сбой широким except; при оборачивании сохраняй причину и не включай секретные входные данные в сообщение.
- При изменении формы данных проверь границу валидации, сериализацию и потребителей. Ориентируйся на фактическую версию Pydantic/библиотеки, её настройки и существующие схемы.

## TypeScript и React

- Не подменяй runtime-валидацию внешних данных утверждением типа `as` или `!`. Проверь, откуда появляется значение и как обрабатывается отсутствие/ошибка.
- У async-обработчиков проверь потерянные promises, порядок ответов и поведение после отмены запроса или смены параметров. Используй уже выбранный проектом механизм запросов и кэша.
- В React сохраняй порядок вызова hooks, проверь зависимости effects, очистку подписок и таймеров, устойчивость ключей списков. Проверь применимость API к установленной версии React, не переноси примеры новой major-версии автоматически.
- Изменение общего компонента или формы API проверь у реальных потребителей, включая состояния загрузки, ошибки и пустого результата. Отдельно проверь генерацию типов, если она используется проектом.

## SQL, миграции и ETL

- При изменении сохранённой формы данных проверь совместимость чтения старых строк и порядок выкладки производителей/потребителей. Для NOT NULL или нового обязательного значения нужен обоснованный переход существующих данных.
- Для миграции опиши эффект на непустой базе, блокировки и принятую в проекте стратегию отката/восстановления. Не выполняй миграцию рабочей БД по поручению изменить код.
- Для пересчёта/ETL проверь повторный запуск, частичный сбой, дедупликацию, границы периода и часовой пояс. Добавление поля без backfill не означает, что исторические данные готовы.
- SQL-параметры передавай через поддерживаемый API драйвера/ORM. Динамические имена таблиц/колонок требуют отдельного контролируемого выбора.

Наличие такого риска — повод проверить достижимый сценарий. Само несоответствие предпочтительному приёму не является дефектом; его последствия и серьёзность устанавливаются по коду и проверкам.
