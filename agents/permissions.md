# Работа с ограниченным профилем

Профиль `kit-restricted` выбирается для новой сессии явным запуском `scripts/permissions.py run --project PROJECT`. Не переключай текущую сессию и не расширяй права автоматически. Управляемая политика может запрещать этот профиль или ограничивать его сильнее локальной настройки.

- Каталог проекта и находящиеся в нём worktree доступны для записи; временные файлы направляются в `PROJECT/.engineering-kit/tmp`. Вне выбранного проекта запись запрещена. Для kit нужна отдельная сессия с `--kit-development`; не добавляй kit во все writable roots.
- Сохраняй защиту Git/Codex-служебных каталогов. Для изменения Git-метаданных используй привязанные к проекту `kit_git_*` по `agents/integrations.md`. Их доверенный backend выполняет HTTPS-авторизацию и разрешённые операции, не выдавая токен shell. Не ослабляй `.git` и не переходи на full access. Если `kit-git` отсутствует, попроси перезапуск через `kit`; обычный shell fetch/commit может быть заблокирован.
- Секреты не читаются shell-командами. Не запускай MCP вручную из командной песочницы для обхода запрета и не выполняй `env`, `source` или команды извлечения токенов. Файл общих подключений читает доверенный MCP-процесс. Программа kit и используемые им MCP-зависимости должны оставаться недоступными проектной сессии на запись.
- Сеть команд проходит через включённый штатный прокси. Без локальной конфигурации разрешены только публичные `github.com` и `api.github.com`; дополнительные имена задаются в игнорируемом `.engineering-kit/local.json`. Для частных сервисов нужны явные точные списки хостов; localhost и произвольные IP автоматически не добавляются. Реестры пакетов и локальные сервисы требуют отдельного согласования.
- MCP работают за пределами командного сетевого прокси. Этот профиль дополнительно передаёт каждому MCP точный список допустимых имён через несекретную переменную `KIT_MCP_ALLOWED_HOSTS`; адаптер проверяет её перед запросом. Это ограничение доверенного адаптера, а не независимый OS firewall для MCP.
- `on-request` не требует подтверждать каждое чтение/тест. Публикация, push и инфраструктура требуют отдельного согласия. `.rules` дают дополнительную проверку запросов вне песочницы, но не гарантируют перехват каждого скрипта, API или эквивалентной записи. `confirm=true` — аргумент MCP, не доказательство согласия; для трёх MCP-инструментов комментариев профиль дополнительно выставляет `approval_mode="prompt"` и проверяющего `user`.
- Для init, configure, prepare, commit, push и cleanup Git MCP запуск через kit выставляет `approval_mode="prompt"`. Это отдельные ограничения инструментов; их процессы не наследуют командный сетевой прокси. Авторизация Git живёт в памяти процесса, HTTPS-адрес выводится из разрешённого origin. Произвольный shell, URL, force и создание PR этим MCP не предоставляются.
  После применения общей политики `kit policy` prepare не требует второго технического подтверждения после согласования задачи; commit также выполняется без него только при явно выбранном `local_commit=auto`. Init/configure, push и cleanup остаются с подтверждением пользователя. Политика не отменяет согласование репозиториев/веток, переключения ветки и включения чужих правок.
- В режиме current commit/push разрешены в явно выбранной ветке разработки (например, dev). Main/master и целевая ветка исключены. Изменение режима/веток не переключает checkout. Исходная папка current не может быть удалена очисткой kit. Ограничения shell, секретов и Git-метаданных сохраняются.
- Не заменяй проверки пользователя автоматическим подтверждением. Если защита или разрешение отсутствуют, обозначь это как ограничение, а не как успешное выполнение. Требования к разбору замечаний по одному остаются в силе.

Запреты по маскам в Linux/WSL действуют на набор найденных файлов при запуске каждого sandbox-процесса и на ограниченную глубину поиска. Они не гарантируют сокрытие секретного файла, созданного позднее внутри уже работающего процесса. Точные запреты и реальный путь существующих симлинков проверяются дополнительно; не обещай полной защиты от произвольно названного или нового секрета.

## Общая политика команд

`kit policy` показывает изменения пользовательского `config.toml`, отдельного управляемого блока глобальных AGENTS, файла `rules/kit-autonomy.rules` и локальных настроек `kit-autonomy.json`. Предпросмотр не пишет файлы. После согласования `kit policy --apply TOKEN` применяет именно этот набор; изменение исходных файлов или выбранных параметров требует нового токена. При переданных параметрах повтори их при применении. Действующие пользовательские правила и остальная конфигурация сохраняются; режим auto-review не включается. Неоднозначный TOML или чужой файл вместо управляемого останавливает запись. Каждая замена файла атомарна, но вся группа не является транзакцией: при ошибке записи проверь фактическое состояние повторным предпросмотром.

По умолчанию локальный commit, восстановление зависимостей, новые зависимости и сервисы требуют согласования. `--local-commit auto` и `--locked-dependencies auto` — отдельные явные предпочтения пользователя. Последний режим разрешает только восстановление по существующему lock-файлу без изменения manifest/lock, не произвольный install. Границы сети/файлов остаются прежними; автоматических разрешений интерпретаторов для выхода из песочницы нет.

`--artifact-root PATH` добавляет выбранную существующую папку в общую настройку запусков kit; можно повторить флаг для нескольких папок. Если флаг не передан, прежний список сохраняется; при передаче задаётся полный новый список. Профиль kit даёт запись в эти точные каталоги с защитой масок секретов и служебных каталогов в их корне. Это не выбор основного места артефактов и не настройка обычного запуска codex: фактическую папку документации всё равно задаёт хаб/задача. Симлинки, каталоги с доступом к настройкам Codex/kit и широкие родительские пути отклоняются. При перемещении/удалении разрешённого каталога требуется обновить политику; нельзя молча расширять доступ.

Для выбранного пользователем vault Obsidian разрешены все его папки, кроме секретных имён: password (включая Password Matrix), secret, credential и «парол» без учёта регистра, а также прежних масок `.env`, ключей и авторизации. Запрещены чтение и запись. При старте kit имена существующих объектов проверяются на всей глубине без чтения содержимого; запрещаются и реальные цели секретных симлинков. Маски дополнительно применяются при старте sandbox-процессов в пределах `glob_scan_max_depth`. Новый секрет глубже этого лимита, созданный после запуска сессии, или секрет с неизвестным именем не гарантированно скрыт. Это ограничение штатного snapshot-механизма, а не разрешение читать такой файл.

Глобальные правила действуют в следующих сессиях Codex этого пользователя WSL, в том числе без kit. Дополнительные ограничения выбранного профиля, управляемые требования и проектные инструкции могут быть строже. `kit rollback` отключает прежний профиль, но не удаляет независимо применённую общую политику. Для проверки решений используй `codex execpolicy check`; это анализ команды, а не её запуск. Префиксы не покрывают произвольные скрипты, SQL внутри приложения и все варианты опций, поэтому оценка реальных последствий агентом остаётся обязательной.

## Самостоятельная локальная работа

`kit policy --local-commit confirm --locked-dependencies auto` показывает режим с меньшим числом согласований. После сверки примени те же параметры с `--apply TOKEN`. Изученные локальные build/lint/types/tests, правки в рамках задачи и обычные артефакты в разрешённых папках выполняются самостоятельно. Восстановление зависимостей допускается только по имеющемуся lock, в окружении проекта и без изменения manifest/lock; сначала проверь scripts и их реальные последствия. Для uv нужен `sync --locked`, для pnpm — `install --frozen-lockfile`, для Yarn — соответствующий версии immutable/frozen режим; npm использует `ci`.

В этом режиме kit убирает свои общие prompt-правила для операций восстановления, поэтому `uv sync --help` и `npm ci --help` также не требуют этих подтверждений. Это снятие лишнего prompt, а не allow-правило для выхода из sandbox. Префиксные правила не доказывают наличие lock-флага, безопасность scripts или изоляцию БД: это проверка агента перед запуском. Другие пользовательские правила, неизвестные команды и действительные границы доступа могут по-прежнему потребовать подтверждение. Для возврата используй preview/apply с `--locked-dependencies confirm`.

Commit, новые зависимости, сервисы, миграции, удаление пользовательских данных и публикации сохраняют ручное согласование; секреты и закрытые каталоги БД остаются запрещены. Auto-review не включается. Prompt-правила kit сохраняются и для `rtk proxy COMMAND`, включая commit и опасные операции; широкие allow для Python/Bash/curl не добавляются. Свои процессы, тестовые данные и cache изолируй от рабочих сервисов. Изменённая политика применяется при новом запуске через kit или kit resume; текущая сессия сама границы доступа не меняет.

## Общая и проектная сетевая политика

`kit policy --network-profile python --network-profile node` показывает точные домены публичных реестров для всех будущих запусков kit. После сверки примени тот же набор с `--apply TOKEN`. Настройки хранятся лично в `kit-autonomy.json`, в проекты не записываются. Это политика команд kit; отдельные запуски Codex без kit и MCP имеют собственные сетевые границы.

`kit policy --project /absolute/project --network-allow registry.private.example` добавляет домен только выбранному проекту и его вложенным рабочим папкам. Соседние проекты его не наследуют. Общие разрешения наследуются всеми проектами; запреты из исходного профиля, общей политики и всех применимых проектных дополнений имеют приоритет над allow. `--network-deny HOST` добавляет запрет, `--network-remove HOST` удаляет только собственные записи выбранной области. Эти действия тоже требуют preview/apply. Проектная команда не меняет режим commit, зависимости или artifact-root.

`kit network --project /absolute/project` без записи показывает эффективную политику, найденные manifest/lock-файлы, недостающие и явно запрещённые домены. Перед восстановлением зависимостей проверяй фактическую папку задачи: её manifest может отличаться от исходного репозитория, а правила родительского проекта наследуются. Сейчас автоматически распознаются Python и Node.js; произвольные точные DNS-домены доступны через `--network-allow`. Поиск ограничен глубиной, размером и количеством manifest, пропускает зависимости, старые worktree, служебные папки, секретные имена и симлинки. Dotenv, npm-конфиги и файлы авторизации не читаются; URL с авторизацией или query не используются. Обнаружение потребности не выдаёт доступ. При старте kit сообщает о недостающих доменах; подробности и ограничения поиска доступны через `kit network`.

Прокси и подтверждения остаются включены. Сетевое разрешение не разрешает установку зависимостей, commit, публикацию или запуск сервисов: действуют выбранные режимы и согласования. При уже разрешённой сети выполняй согласованное восстановление зависимостей в обычном sandbox с предназначенными для задачи cache/config; технические подтверждения правил сохраняются. Применение общей сетевой политики требует новой сессии kit; оно не исправляет ошибку native `require_escalated` и лимит аргументов bubblewrap. При неизвестном отказе не расширяй права автоматически: сначала определи нужную границу и покажи точное изменение.

## Проверенный backend Codex

Для исправления native-дефекта можно выбрать отдельно собранный и проверенный standalone backend через `kit policy --runtime-executable /absolute/codex-home/kit-native/BUILD/bin/codex`. Файлы должны находиться в личном каталоге Codex/kit-native, в отдельной папке сборки без симлинков. Preview читает метаданные и SHA256 фиксированных компонентов, не исполняет кандидат. После сверки применяется тот же параметр с `--apply TOKEN`. Выбор общий для всех проектов kit; системная команда codex не заменяется. Это не автоматическая сборка или разрешение скачать новые зависимости.

При каждом старте kit сверяет содержимое и идентичность компонентов. Изменение, подмена или удаление файла останавливает запуск; автоматической загрузки или возврата к другому binary нет. Служебные hard link сессий не отзывают разрешение. Папка backend защищается от записи обычной проектной сессией. Выбранный backend запускается с `--no-daemon`, чтобы не передать работу общему серверу старого binary; проверка обновлений при его старте отключена, обновление требует нового согласованного снимка. Sandbox и подтверждения сохраняются. `kit policy --clear-runtime` показывает отзыв выбора, который применяется по токену; сами файлы не удаляются, сетевая политика сохраняется. Это возвращает системный Codex вместе с его известными ограничениями.

Обычный запуск — `cd PROJECT` и `kit`. Для продолжения с тем же backend и текущей политикой: `kit resume UUID` либо `kit resume --last`; `--project PATH` выбирает рабочую папку, а `--kit-development` нужен для работы над самим kit. Запускай resume из достоверной директории сессии, указанной в её артефактах. Обычный `codex resume` использует системный Codex и не выбирает согласованный backend kit.
