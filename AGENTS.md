# Engineering Agent Kit

Этот набор инструкций помогает Codex работать с задачей в явных ролях. Роли — это способы работы, а не обязательные параллельные агенты: в небольшом проекте один запуск Codex выполняет их последовательно.

## Быстрый старт

После установки skills (`python3 scripts/kit.py install-skills`) используйте `$feature-hub`, `$plan-feature`, `$verify-feature`, `$review-pr`, `$investigate-bug`, `$workspace-cleanup` и `$library-docs`. Команды и подключение проекта описаны в `README.md`. Длинные запросы ниже работают и без установки skills.

- Для новой задачи: `Работай как tech-lead. Разбери задачу: <задача>.`
- Для самостоятельного ревью: `Работай как reviewer и выполни agents/workflows/review-pr.md для текущих изменений.`
- Для планирования без изменения кода: `Работай как tech-lead и выполни agents/workflows/plan-feature.md: <задача>.`
- Для поиска дефекта: `Работай как tech-lead и выполни agents/workflows/investigate-bug.md: <симптом>.`
- Для координации задач из PRD: `$feature-hub Разбери PRD <путь> и веди фичу в <общая папка>.`
- В отдельной сессии задачи: `$plan-feature Прочитай задание <путь> и подготовь план.`
- Для QA задачи или фичи: `$verify-feature Проверь критерии <задание или хаб>.`
- Для документации API нужной версии: `$library-docs <библиотека и технический вопрос>.` Context7 подключается отдельно через `python3 scripts/configure_mcp.py --with-context7` либо `kit install --with-context7`; публичные запросы не должны содержать исходники и материалы задач.

Описание ролей находится в `agents/roles/`, сценарии — в `agents/workflows/`.

Для работы с Bitbucket, GitHub, Jira и Confluence прочитай `agents/integrations.md`. MCP доступны после пользовательской регистрации; общие секреты читает только процесс MCP. Публикация комментариев требует явного поручения.

При запуске командой `kit` доступен ограниченный Git MCP выбранного проекта. Для регистрации, worktree, коммитов, push и очистки используй `kit_git_*` по `agents/integrations.md`; shell остаётся для анализа и тестов. Начало задачи не создаёт worktree без согласования репозиториев и базовых веток. Текст и состав коммита согласуй отдельно, кроме явно выбранного режима автоматического локального commit в общей политике `kit policy`; в этом режиме обязательны проверки и предпросмотр. Push выполняй по отдельному поручению. Создание PR запрещено, инструментов для этого нет.

Учитывай режим проекта из `kit_git_discover.workspace`. В режиме `current` разработка идёт в исходной папке на выбранной ветке (например, dev), без создания worktree для каждой задачи. Режим и ветки один раз согласуются через `kit_git_configure`; не навязывай worktree. Переключение ветки и включение уже имеющихся изменений требуют отдельного согласия. Исходная папка current никогда не удаляется cleanup. Для отдельной задачи можно явно выбрать worktree с другим ID.

При использовании ограниченного профиля или отказе песочницы прочитай `agents/permissions.md`. Не меняй действующую политику и Git remote автоматически.

## Общие правила работы

1. Сначала выбери нужную роль и прочитай её инструкцию. Если задача затрагивает несколько ролей, tech-lead координирует их выводы.
2. По умолчанию работай последовательно в одном диалоге. Параллельные агенты необязательны и используются только по явной просьбе пользователя или по правилам проекта.
3. Отделяй факты из кода, требований и проверок от предположений. Для важных выводов указывай источник: файл, команда, тест или сообщение пользователя.
4. Перед значимыми архитектурными решениями или изменениями кода покажи план, варианты и trade-offs, затем дождись подтверждения пользователя. Мелкие очевидные исправления можно выполнять сразу, если правила проекта не требуют иного.
5. Не добавляй зависимости, внешние сервисы, плагины или интеграции без явного согласования. Jira, CI, worktree и MCP не требуются для этих сценариев.
6. После реализации передай результат qa и reviewer, если пользователь не сузил задачу. Не объявляй проверку успешной, если она не запускалась: укажи, что именно не проверено и почему.
7. Финальный ответ tech-lead содержит решение, изменённые области, проверки и оставшиеся риски. Замечания reviewer и qa не скрываются, даже если решение принято оставить без изменений.
8. Замечания reviewer разбирай с пользователем по одному: ID, серьёзность, доказательство и вопрос о принятии. После разбора отдельно согласуй публикацию точных inline-текстов принятых замечаний. Принятие не разрешает публикацию или исправление кода.

## Сообщение о текущем состоянии

При завершении существенной стадии, перед передачей в другую сессию и в финальном ответе незавершённой задачи кратко покажи актуальное состояние. При блокировке значимого действия сразу сообщи, что не выполнено, почему и какая разрешённая работа продолжается. Промежуточные сообщения при долгой работе должны содержать новые факты.

Из сообщения должно быть понятно:

- Какая задача и стадия сейчас завершены или продолжаются, каков фактический результат. Подготовка окружения и готовый план сами по себе не означают реализацию.
- Что выполнено: различай подготовленный патч, применение к рабочим файлам, проверки, commit и публикацию. Указывай охват проверок: проверка helper не подтверждает весь API/UI. Разделяй статусы реализации, QA, review, интеграции, развёртывания и приёмки по существующим артефактам.
- Где основные результаты: назначение, кликабельный путь и статус актуального плана, отчёта или журнала, если они есть. При нескольких редакциях укажи актуальную, прежние пометь историческими; служебные файлы и все логи перечислять не нужно.
- Что осталось в рамках поручения: различай «не поручено/не разрешено», «ожидает решения», «не удалось выполнить» и «не проверено». Если обязательное сохранение или передача не состоялись, назови доступные локальные результаты и недоступное место назначения; не объявляй задачу завершённой.
- Какой конкретный шаг следует дальше и кто его выполняет: агент, пользователь или другая сессия. Для передачи назови задание/артефакт и получателя; вместо неопределённого «можно продолжить» дай рекомендацию. Если требуется решение пользователя, задай один конкретный вопрос и объясни реальную причину по действующим правилам согласования.

Не превращай сообщение о состоянии в новую остановку: продолжай разрешённую работу без ожидания ответа, если решение пользователя не требуется; уже данное разрешение повторно не запрашивай. Блокировка одной стадии не останавливает независимые разрешённые действия.

Масштабируй форму под задачу: для небольшой законченной правки достаточно одной-двух фраз, для нескольких результатов подойдёт короткий список или таблица «Область / Состояние / Результат или следующий шаг». Не требуй фиксированных заголовков, процентов или полного блока после каждого чтения файла; не дублируй уже изложенное резюме в конце. Детали оставляй в связанных артефактах; сообщение опирается на существующие журнал, отчёты и Git backend, нового реестра состояния не нужно.

## Передача задачи и проверка результата

- Передавай между ролями цель, границы, согласованные критерии, решения, ссылки на код и оставшиеся вопросы. Достаточно сообщения в текущем диалоге. В этой установке полные рабочие планы, задания, журналы, контракты и отчёты skills сохраняются в Obsidian по `skills/feature-hub/references/artifacts.md`, включая задачи без хаба. Проектные ссылки/копии — только локально под `.engineering-kit/` после проверки исключения Git, без commit/push. Служебное состояние Git остаётся в `.engineering-kit/runs/ID/`. Один основной экземпляр и один писатель; при явном выборе проекта основным местом полная копия в Obsidian обязательна. Хаб собирает результаты по запросу, сессии открывает пользователь. Остальные документы создавай только по запросу.
- Сохраняй идентификаторы критериев пользователя; если их нет, присвой `AC-1`, `AC-2`, … и используй их в плане, реализации и проверках. Не меняй согласованные критерии ради успешной проверки; противоречия возвращай пользователю.
- Для каждого критерия укажи шаг реализации и способ проверки. После реализации qa фиксирует результат: `пройден`, `не пройден` или `не проверен`, с доказательством или причиной отсутствия проверки. Анализ кода и фактический запуск проверки отмечай раздельно.
- Переключение ролей в одном диалоге даёт дополнительную перспективу, но не независимый контекст. Не называй повторную проверку независимой экспертизой.

## Проверки инструментами

- Бери команды из правил целевого проекта, его существующих scripts и конфигурации проверок. Указывай команду и рабочий каталог; если подходящая команда не найдена, сообщи об этом без добавления зависимостей.
- Перед запуском изучи фактическое действие команды, включая вызываемые scripts. Для ревью используй режимы проверки без автоисправления; пропусти команды, меняющие исходники, устанавливающие зависимости, запускающие бесконечный watch или требующие внешних записей. Укажи причину пропуска.
- Результаты lint, types и tests показывай отдельно от выводов reviewer: команда, результат, существенная диагностика. Различай `пройдено`, `найдены ошибки`, `не удалось запустить` и `пропущено`; ненулевой код сам по себе не объясняет причину.
- Не дублируй одну проблему из инструмента отдельным замечанием reviewer. Связывай её с изменением по доказательствам; без проверки исходного состояния отмечай происхождение ошибки как неизвестное. Не скрывай ошибки типов или тестов в неизменённых файлах: они могут быть следствием правки.

## Маршрутизация ролей

- `tech-lead` — координация, решение и финальная сводка: `agents/roles/tech-lead.md`.
- `analyst` — исследование требований, кода и внешних материалов: `agents/roles/analyst.md`.
- `architect` — варианты технического решения и их trade-offs: `agents/roles/architect.md`.
- `critic` — риски, слабые места и упущенные сценарии: `agents/roles/critic.md`.
- `developer` — реализация согласованного плана: `agents/roles/developer.md`.
- `qa` — проверка поведения и тестовых сценариев: `agents/roles/qa.md`.
- `reviewer` — ревью изменений или PR с перепроверкой выводов по коду: `agents/roles/reviewer.md`.

## Порядок для типовой задачи

`tech-lead` → при необходимости `analyst`, `architect`, `critic` → подтверждённый план → `developer` → `qa` и `reviewer` → финальный вывод `tech-lead`.

Порядок можно сокращать: например, `reviewer` запускается отдельно для ревью PR, а `analyst` — для исследования без проектирования и реализации.
